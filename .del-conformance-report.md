# Full-envelope round-trip fix — noy-db-to

Date: 2026-07-09
Branch: `chore/del-conformance`

## 0. Why this supersedes the prior `_del`-only pass

The prior commit on this branch (`fix: preserve _del delete-marker across field-mapped stores`)
fixed the four field-mapped stores by adding one more named column/attribute (`del`) alongside
the existing `by`/`tier`/`elevated_by`/`det` per-field mapping. That's a **whack-a-mole** fix: it
only helps the one field someone happened to test for, and still silently drops any envelope
field the item-mapper doesn't explicitly enumerate — most importantly **`_cek`** (the wrapped
per-record content-encryption key used by `perRecordKeys`/classified-fields/blobs/`forget()`) and
**`_debug`**, neither of which the prior pass added. Losing `_cek` on round-trip makes the record
**permanently undecryptable** — a silent data-loss bug, not a cosmetic one.

This pass replaces the per-field enumeration with a **systemic fix**: each store now persists the
*entire* envelope as one opaque JSON blob (`env` column / `_env` attribute), and only keeps
`vault`/`collection`/`id` (routing) + `v` (CAS) + `ts` (ordering) as real, queryable
columns/attributes. Every current and future envelope field (`_cek`, `_debug`, `_source`,
`_sourceTs`, `_sealed`, `_vdig`, `_bidx`, …) now survives automatically — nothing to remember to
add next time hub grows a field.

## 1. The real envelope shape (confirmed from `@noy-db/hub@0.3.0-pre.7`'s `.d.ts`)

`EncryptedEnvelope` (`node_modules/.../@noy-db/hub/dist/index-BJ3L-XcV.d.ts:18995`) has far more
optional fields than the four field-mapped stores ever mapped: `_by, _source, _sourceTs, _tier,
_elevatedBy, _det, _sealed, _vdig, _bidx, _cek, _debug, _del`. None of the four stores mapped
`_source`/`_sourceTs`/`_sealed`/`_vdig`/`_bidx` either — the systemic fix closes all of these at
once, not just the two named in the task.

mock.) Working tree was restored via `git stash pop` immediately after capturing this evidence; the
temporary test file was deleted, not committed.

## 4. Migration note (same text added as a doc comment at each store's DDL/schema site)

> New writes only populate the routing keys + `v`/`ts` + `env` (`env` = `JSON.stringify(envelope)`,
> the entire envelope). Legacy per-field columns (`iv`, `data`, `by`, `tier`, `elevated_by`, `det`,
> `del`) are retained, nullable, **only** so rows written before this change keep reading correctly
> via a dual-read fallback in `rowToEnvelope`/`itemToEnvelope` (env present → parse it; env absent →
> reconstruct from the legacy columns). No data migration script is required (pre-1.0).

## 9. Critical fix wave — legacy-table migration + strict null-check + test coverage

A whole-branch review of §1–8 above found 2 Criticals + 1 Important. This section documents the
follow-up fix, applied as a new commit on top (not amended, per instructions).

### Critical 1 — SQL stores had no migration path for pre-existing tables

`CREATE TABLE IF NOT EXISTS` is a no-op against a table that already exists — an upgraded
deployment's table had **no `env` column at all**, so every write failed (`no column named env`),
the legacy `iv`/`data` `NOT NULL` columns rejected the env-only insert, and `listPage`'s explicit
`SELECT … env` failed outright. The dual-read fallback (the whole safety net from §1–8) was
therefore unreachable for real legacy rows.

Fix, same shape in all three SQL stores — **d1** (`to-cloudflare-d1/src/index.ts`), **sqlite**
(`to-sqlite/src/index.ts`), **turso** (`to-turso/src/index.ts`):

1. **ALTER TABLE migration**, run right after `CREATE TABLE IF NOT EXISTS`:
   - `to-cloudflare-d1/src/index.ts:96-101` — `await db.prepare('ALTER TABLE … ADD COLUMN env TEXT').run()`
     wrapped in try/catch inside `ensureSchema()`.
   - `to-sqlite/src/index.ts:108-114` — `db.exec('ALTER TABLE … ADD COLUMN env TEXT')` wrapped in
     try/catch, synchronous (constructor-time), right after the `CREATE TABLE` `db.exec()` call and
     before the `CREATE INDEX` statements.
   - `to-turso/src/index.ts:83-88` — `await client.execute('ALTER TABLE … ADD COLUMN env TEXT')`
     wrapped in try/catch inside `ensureSchema()`.
   - All three swallow **only** an error whose message contains `duplicate column name`
     (case-insensitive) — thrown when `env` already exists (i.e. the table was just created fresh by
     the DDL above, or a prior process already ran the migration) — and rethrow anything else.
     Idempotent by construction: fresh table → duplicate-column → swallowed; legacy table → column
     added.
2. **Writes keep binding `envelope._iv` / `envelope._data`** into the legacy `iv`/`data` columns —
   they're always-present real values, so they keep satisfying the un-droppable `NOT NULL` on
   legacy tables. Reads stay env-authoritative (`rowToEnvelope`/parses `env` first; `iv`/`data` are
   only read in the legacy fallback branch), so this can't shadow the env value.
   - `to-sqlite/src/index.ts:149-163` (`upsert`, the single write site for `put`/`saveAll`/`tx`) — INSERT
     column list now `(vault, collection, id, v, ts, env, iv, data)`, `ON CONFLICT … DO UPDATE SET`
     extended with `iv = excluded.iv, data = excluded.data`.
   - `to-cloudflare-d1/src/index.ts:136-148` (`upsertStatement`, the single write site) — same column
     list + `ON CONFLICT` extension.
   - `to-turso/src/index.ts` — **all 5 write sites** updated: create-only `INSERT OR IGNORE` (:154-162),
     update-only `UPDATE … SET v=?, ts=?, env=?, iv=?, data=?` (:166-184, args reordered to
     `[v, ts, env, iv, data, vault, collection, id, expectedVersion]`), unconditional upsert
     (:191-198), `saveAll`'s inline batch-insert (:269-278), `tx`'s inline put-op SQL (:326-336).
3. **DDL**: `iv`/`data` reverted from the nullable form introduced in §1–8 back to `NOT NULL` (matching
   the pre-existing legacy schema exactly), now that every write path always supplies real values —
   `to-sqlite/src/index.ts:96-97`, `to-cloudflare-d1/src/index.ts:85-86`, `to-turso/src/index.ts:73-74`.
   `env` stays nullable (existing legacy rows won't have a value until rewritten).
   `listPage`'s explicit `SELECT id, v, ts, env, iv, data, by, tier, elevated_by, det, del` was
   **audited and left unchanged** in all three stores: every one of those columns is guaranteed
   present in both a fresh table (full DDL) and a migrated legacy table (original DDL + the `env`
   ALTER only adds `env`, it never had fewer columns to begin with) — so no column-trimming was
   needed there. `get`/`loadAll` already use `SELECT *`, unaffected either way.

**Dynamo** (`to-aws-dynamo/src/index.ts`) is schemaless — left untouched, per instructions.

### Critical 2 — sqlite strict null check crashed legacy reads

`to-sqlite/src/index.ts:112` (`rowToEnvelope`) — `if (row.env !== null)`. On a legacy table
`SELECT *` yields `row.env === undefined` (column doesn't exist), and `undefined !== null` is
`true`, so `JSON.parse(undefined)` ran → `SyntaxError` on every `get`/`loadAll` against a legacy
row. Changed to the loose check `if (row.env != null)` — now `undefined` and `null` both fall
through to the legacy reconstruction branch. Verified `to-cloudflare-d1/src/index.ts:106` and
`to-turso/src/index.ts:95` already used the loose `!= null` form (confirmed by direct read); no
other store had the strict form.

## 13. listPage del-column fix

Follow-up to §9's Critical-1 note ("`listPage`'s explicit SELECT … was audited and left
unchanged … every column guaranteed present") — that audit was wrong. Verified against
commit `c2fd829` (the actually-published legacy schema, before *any* `_del` support existed):
none of the three SQL stores' original DDL had a `del` column. `del` was introduced only by
the later, superseded `_del`-only commit `0864111`; the systemic `env` migration's `ALTER
TABLE … ADD COLUMN env` (§9) adds `env` only, never `del`. So a genuinely upgraded/legacy
table has no `del` column, and `listPage`'s explicit `SELECT … del` throws `no such column:
del` on it. `get`/`loadAll` (`SELECT *`) are unaffected.

### Fix — drop `del` from `listPage`'s explicit SELECT

- `to-sqlite/src/index.ts:255` — `SELECT id, v, ts, env, iv, data, by, tier, elevated_by, det, del FROM …`
  → `SELECT id, v, ts, env, iv, data, by, tier, elevated_by, det FROM …`
- `to-cloudflare-d1/src/index.ts:260` — same column-list edit.
- `to-turso/src/index.ts:304` — same column-list edit.

All other selected columns (`env`, `iv`, `data`, `by`, `tier`, `elevated_by`, `det`) are
guaranteed present on both a fresh table (full current DDL) and a migrated legacy table
(original `c2fd829` DDL + the `env` ALTER), so none of them needed dropping.
`rowToEnvelope`'s legacy fallback was left untouched: a real legacy row has no `del`, so
`row.del` is simply `undefined` (property absent, not selected) → `_del` correctly stays
unset, same as before.

**No other explicit SELECT needed the same fix** — audited every `SELECT` in all three
stores; the only other explicit-column selects are `SELECT v FROM …`, `SELECT id FROM …`,
and `SELECT 1`, none of which reference `del` or any other non-guaranteed column. `get`/
`loadAll` use `SELECT *` throughout.

Three hand-written test mocks hardcoded the old 11-column SQL string and had to be updated
to match (otherwise they'd throw "unsupported SQL" against the new query):
`to-sqlite/__tests__/to-sqlite.test.ts:70`, `to-cloudflare-d1/__tests__/to-cloudflare-d1.test.ts:49`,
`to-turso/__tests__/to-turso.test.ts:71`.

### Migration-test extension

`to-sqlite/__tests__/migration.test.ts`'s "OLD DDL" table itself had a residual bug matching
the one being fixed: it modeled "legacy" as a post-`0864111`/pre-systemic-fix table (DDL
included `del INTEGER`, seeded a `del` value, and asserted `_del: true` on readback) instead
of the genuinely published `c2fd829` legacy schema, which has no `del` column at all. Since
`del` *was* present, the old test could never have caught this bug. Corrected the OLD DDL to
drop `del` entirely (and the corresponding insert column/value and the `_del: true` assertion
on the legacy-row readback, since a truly legacy row has no delete-marker data to reconstruct),
then added the `listPage` assertion:

```ts
const page = await store.listPage('v1', 'c1')
expect(page.items.map(item => item.id)).toEqual(['legacy1', 'new1'])
```
